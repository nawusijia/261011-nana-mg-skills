# 娜娜 MG｜视觉自检闭环 V1 · 先看见错误，再允许交付

> **最高优先级：不是「程序跑通→所有项全绿」，而是「把实际画面渲出来→亲眼观察→指出缺陷→改代码/素材→重渲同一镜头确认→检查完整视频」。**
> 适用于需要原创 MG/3D/2.5D/SDF、关键美术镜头或大幅修改的项目。简单字幕微调只审受影响帧和上下文，不机械要求整片四轮。

## 0. 输出状态不得混淆

- **TECH_PASS**：编码、音轨、尺寸、时间轴、文件存在等**机器事实**正确。此状态**绝不表示画面通过**。
- **VISUAL_NOT_REVIEWED**：只有脚本/拼图生成，没有 Agent 实际打开、看过截图；**不能称自检完成**。
- **VISUAL_FAIL / REWORK**：看到穿模、变形、闪烁、焦点丢失、难看、节奏不对、文字不清、遮挡、空镜等实际画面问题；记录时间位置，直接返工。
- **VISUAL_SELF_REVIEWED**：Agent 已看清关键局部/连帧，针对发现问题做过修复并对比，新版未看到可识别的阻断缺陷。**不是用户验收**，不能换个措辞叫「全部通过/零缺陷/定稿」。若仍明显丑、没惊喜，继续返工或报告不足。
- **AWAITING_USER_REVIEW / USER_ACCEPTED**：只有用户实际观看并确认后，才能写 USER_ACCEPTED。

所有自动工具只能证明**有文件、有截图、有记录、有轮次**。它们不能判断截图好不好看，**不能给「视觉绿灯」**。

## 1. 强制工作循环（有严重缺陷即阻断高清最终宣告）

1. **每一轮实际渲染**：优先关键镜头多张真实渲染帧，不是用源代码、几何计算、网页布局截图或文字想象画面。至少首/中/高潮/尾，转场前后、角色出入场、复杂物体接触位。
2. **真正用视觉打开**：让执行 Agent 用可看图的工具打开并观察生成的实际图片（例如能读取并显示 JPG 的文件工具）。只输出文件路径、生成 contact-sheet 或终端“PASS”**不算看过**。如果工具根本无法查看图像，必须明确标记 VISUAL_NOT_REVIEWED，不准猜。
3. **像克肆一样主动找茬**：每轮逐项审「观众看懂吗、焦点够大吗、画面哪里丑、有没有突兀、有没有没有价值的装饰」，加查 `穿模/重叠/漂浮/狗牙/反屋顶/共面闪烁/文字渲染/灯光/主体跑出画面/变形跳切/乐感节奏`。挑**实际可指认的画面区域**，不编造问题以填表。
4. **写清证据，真正修改**：记录视频文件、秒数/帧号、截图、问题、严重性、预期画面、代码/材质/镜头的精确修复。先改高优先级结构错误；不要靠音乐或模糊特效掩盖。留 V1/V2 前后图，至少一处使用**相同时间、机位、画幅/缩放**对比修复前后。
5. **重新渲并再看**：不能拿旧截图当新证明；同一问题经修改后**必须重新输出对应帧**，旁边放修复前图，肉眼确认改变是否改善、有没有新毛病。变化一处，又影响另一处时继续迭代。
6. **完成低清全片并再审**：逐时序拼图只是导航；对异常段抽连续 3–10 帧（30fps时逐帧33ms），必要时按秒级局部放大，尤其**移动、碰撞、扇叶、镜头拉远/转换、出字**。完整1080P成片输出后再抽首、末、高潮和本次修复区域看一次，不要只凭低清预览交付。
7. **若仍有问题，宁可诚实报告未完成**：不能写“检查全绿”“已完全解决”，更不能因代码测试通过擅自定稿。用户说画面错就是下一轮的输入，不以数值通过反驳用户亲眼所见。

## 2. 最低执行证据（实用而不无限吃上下文）

| 阶段 | 实际审看片段 | 必须写出的具体观察 |
|---|---|---|
| **首轮定方向** | 6–18张代表性静帧，至少一张主体高清近景 | **哪里不好／哪里好／为什么**，具体到时间和对象 |
| **第一轮返工** | 同秒同镜头 Before/After（视频版本不同），重大运动时加连续帧 | 缺陷、改动、照片变化、是否修好或引入新的问题 |
| **第二轮返工／综合复核** | 完整低清样片 + 约0.33–0.5s时间拼图，复杂动作逐帧检查 | 新缺陷、构图与节奏问题；如全无问题须说明为何 |
| **正式成片复核** | 1080P最终输出，再抽开头/高潮/尾/争议帧高清图 | 实际检查结果与尚待用户确认的审美判断 |

典型原创 3D/MG 至少**三次真正看图的独立审片节点**（首轮、返工、正式片复核），复杂项目争取四轮及以上；不要机械凑“4轮/18张”的数字，有实质错误就继续修直到关键问题消失或用户决定止损。只有纯文字特定小改动时可缩小审片范围，仍须实际看影响画面。

### 实际截图操作示例（来自真实渲染文件）

在独立工程目录里，先建 `visual-qa/`，例如：

```bash
ffmpeg -y -ss 5.50 -i preview-v1.mp4 -frames:v 1 -q:v 2 visual-qa/v1-5.50.jpg
ffmpeg -y -ss 5.50 -i preview-v2.mp4 -frames:v 1 -q:v 2 visual-qa/v2-5.50.jpg
ffmpeg -y -ss 6.00 -i preview-v2.mp4 -frames:v 1 -vf crop=960:540:400:200 -q:v 2 visual-qa/v2-6.00-detail.jpg
```

这是**截取**，不是审片！后续还必须**真的打开这几张图、看得出具体优劣、记录观察**。对比图须同秒同机位。`audit_mg.py` 生成的 480px 时间拼图只能当导航，另抽高清细节才够检查狗牙/风车。使用 `scripts/visual_gate.py --init PROJECT` 生成审片表后，填写每轮的 `shots`：`kind=overview`（全图）、`kind=detail`（细节高清）、`kind=sequence`（连续帧拼图）；每轮至少一张可清晰看细节的图，最后一轮必须有连续帧证据。脚本只检查证据链结构，**不会替你睁眼看片**。

## 3. 反作弊的交付门禁

项目内存一份 `visual-review.json`，按照 `scripts/visual_gate.py --init PROJECT` 生成空模板，执行者**在实际看图后人工填写**；`python scripts/visual_gate.py --check PROJECT` 只核验文件、路径、各轮观察内容、失败→修复→同机位截图证据、是否还有阻断问题。

脚本**不做主观审美判断**；其返回 `EVIDENCE_READY_AWAITING_USER` 仅表示复核证据链齐全。若还没看图、不愿写具体发现、缺少高清对照或仍有未修缺陷，则 `VISUAL_EVIDENCE_INCOMPLETE`。即使脚本退出0也不准把 **EVIDENCE_READY** 写成视觉通过。

**严禁**：自动创建「已审片通过」JSON、程序直接填写主观结论、把生成 contact sheet 当成已观察、用同一张图充当 before/after、用黑帧检测代替穿模/闪烁检查、拿修过源码的描述替代实拍结果。

## 4. 对话汇报方式（给用户看的摘要）

真实做完时，简短讲四件事：**发现哪一帧什么问题、怎么改、重渲看后具体有什么变化、还有哪些仍待确认**。最后给新 MP4 工程路径。无需倾倒几十行绿色检查表或逼用户做 Agent 该做的审核。

**不合格汇报例**：「ffprobe通过、黑帧0、300帧全绿，已完全解决穿模。」
**合格汇报例**：「6.4秒山尖截图仍有阶梯状阴影；提高网格数后没完全好，再改连续法线并做局部平滑，同镜头重渲看见毛刺明显减少；风车7.0–7.1秒逐帧未看到颜色抢层。程序验收另行通过，但尚未得到你的最终看片确认。」

## 5. 可学习的失败案例

《把风装进纸里》（paper-wind-world）多次 V1–V4 返工中暴露了**“每轮报全绿→用户却仍看见穿模、倒屋顶、闪烁、狗牙”**。技术门禁不足以防止视觉审片失败。具体山尖与风车案例见 `../nana-mg-kesi-craft/references/case-ridge-windmill-v4.md`。

不鼓励抄 V4 源码，**应该学习其失败的发现方式、同镜头实图对比，以及用户反馈优先于脚本的原则**。
